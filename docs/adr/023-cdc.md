# ADR-023: CDC (Change Data Capture)

**Status:** Accepted
**Date:** 2026-05-13
**Deciders:** junyoung
**Related:** ADR-022 (MVCC + CAS), ADR-014 (KV State Machine), ADR-019 (Linearizable Read), ADR-012 (Raft Log WAL)

---

## Context

### The gap after MVCC

ADR-022가 완성한 이후, Core-X의 쓰기 경로는 다음을 보장한다:

```
client → Propose → Raft commit → apply() → MVCCStateMachine
                                            ├─ versions[key] 갱신
                                            ├─ CAS 충돌 감지
                                            └─ WaitForIndex 해제
```

하지만 `apply()`가 끝난 순간, 그 변경 사실은 **state machine 안에서만** 존재한다.
외부 시스템이 "key=stock 값이 바뀌었다"는 사실을 알려면 polling 외에 방법이 없다.

```
현재 상황:
  외부 서비스 → GET /mvcc/kv/stock  (매초 폴링)
              → ReadIndex → WaitForIndex → sm.Get
              → 응답: 변경 전과 동일한 값 (아직 apply 안 됨)
              → 응답: 변경된 값  ← 얼마나 지났는지 모름
  
  문제:
  - 불필요한 ReadIndex 트래픽 (Raft leader에 선형 부하)
  - 알림 지연 = polling 주기
  - "이미 본 값인가?" 판단 로직이 소비자에게 전가됨
```

실무 시나리오:

| 서비스 | 필요한 것 | 현재 한계 |
|---|---|---|
| 알림 서비스 | stock=0이 되는 순간 push | polling 주기 = 알림 지연 |
| 검색 인덱서 | 상품명 변경 즉시 재색인 | 변경 여부를 스스로 감지 불가 |
| 감사 로그 | 누가 언제 무엇을 어떻게 바꿨는지 | apply() 이후 기록 불가 |
| 다운스트림 캐시 | 변경 시 무효화 | 변경 감지 방법 없음 |

### DDIA Chapter 11 — Stream Processing 매핑

DDIA Ch.11은 CDC를 다음과 같이 정의한다:

> "Change data capture is the process of observing all data changes written
> to a database and extracting them in a form in which they can be replicated
> to other systems."
> — DDIA Ch.11 §"Change Data Capture"

핵심 통찰: **데이터베이스의 WAL은 이미 변경 이벤트 스트림이다.** CDC는 이 스트림을
외부로 노출하는 메커니즘이다.

Core-X의 WAL = Raft log. `apply()`는 이미 Raft log를 순서 보장하며 소비하고 있다.
CDC는 이 `apply()` 경로에 발행(publish) 단계를 추가하는 것이다.

| DDIA 개념 | Core-X 표현 |
|---|---|
| Database WAL | Raft log (`LogStore`) |
| CDC reader (tail reader) | `MVCCStateMachine.apply()` |
| Event log / change stream | `ChangeLog` (이 ADR에서 도입) |
| Consumer / subscriber | `GET /cdc/stream` SSE 클라이언트 |
| Offset / sequence number | `ChangeEvent.Offset` = Raft log index |
| Log compaction boundary | Raft snapshot index (replay 한계) |

### 실무 도구 매핑

#### MySQL binlog / PostgreSQL logical replication

MySQL binlog와 PostgreSQL의 logical replication slot은 각각 InnoDB redo log,
PostgreSQL WAL을 row-level change stream으로 추상화한다. Core-X의 Raft log +
`apply()`는 이 구조의 단순화된 동치물이다.

| 실무 도구 | Core-X 동치 |
|---|---|
| MySQL binlog position | Raft log index (`ChangeEvent.Offset`) |
| PG replication slot LSN | `lastApplied` 체크포인트 |
| binlog row event | `ChangeEvent{Type, Key, Value, Version}` |
| `SHOW BINARY LOGS` | `GET /cdc/status` (offset 범위 조회) |

#### Debezium

Debezium은 DB WAL을 직접 tail하여 Kafka topic에 발행하는 커넥터다.
Core-X CDC는 Debezium의 simplified 버전이다:

- Debezium: MySQL binlog → Kafka
- Core-X CDC: Raft log (via `apply()`) → SSE stream

#### Kafka consumer group

Kafka는 offset 기반 replay를 지원한다: `consumer.Seek(offset)`.
Core-X CDC도 `?offset=N` 쿼리로 Raft snapshot 범위 내에서 replay를 지원한다.
단, Kafka와 달리 snapshot 이전 offset은 GC됐으므로 재생 불가하다 (아래 §Limitations).

#### Outbox 패턴

Outbox 패턴은 "DB 쓰기 + 이벤트 발행의 원자성"을 보장하기 위해 같은 트랜잭션 내
`outbox` 테이블에 이벤트를 기록하고, 별도 프로세스가 이를 읽어 Kafka에 발행한다.

Core-X에서 이중 쓰기 문제는 발생하지 않는다. `apply()`는 Raft 클러스터 전체에서
exactly-once 순서로 호출되며, CDC 발행은 이 `apply()` 콜스택 내에서 이루어진다.
Outbox가 필요했던 이유(DB 트랜잭션과 MQ 발행 사이의 원자성 갭)가 없다.

## Decision

`MVCCStateMachine.apply()` 완료 시점에 `ChangeEvent`를 발행하는 `ChangeLog`를
도입한다. HTTP 레이어는 `GET /cdc/stream` SSE 엔드포인트로 이를 외부에 노출한다.

구체적으로:

1. `ChangeEvent` 타입 — MVCC version 포함, Raft log index를 offset으로 사용
2. `ChangeLog` — 구독자 관리, bounded buffer 전략, goroutine 누수 방지
3. `MVCCStateMachine`에 `ChangeLog` 통합 — apply 성공 후 발행 (at-least-once)
4. `GET /cdc/stream` SSE 엔드포인트 — HTTP/1.1 text/event-stream
5. `GET /cdc/stream?offset=N` — snapshot 범위 내 replay
6. 통합 테스트 — 쓰기 10건 → SSE 구독자가 순서대로 10건 수신

## Design

### ChangeEvent

```go
// ChangeEvent represents a single committed state change in the MVCC store.
//
// Offset is the Raft log index that produced this event. Consumers use Offset
// to detect gaps, request replays, and implement exactly-once processing on
// their side.
//
// Version is the MVCC version assigned to the key by this write (ADR-022).
// For "del" events, Version is the tombstone version (last version before delete).
type ChangeEvent struct {
    Type      string    // "set" | "del"
    Key       string
    Value     string    // empty for "del"
    Version   uint64    // MVCC version (ADR-022 연동)
    Offset    int64     // Raft log index; monotonically increasing
    Timestamp time.Time // wall clock at apply() time (informational only)
}
```

**Version 필드가 필요한 이유 (MVCC 연동):**

ADR-022에서 `MVCCStateMachine`은 각 write에 단조 증가하는 version을 부여한다.
소비자 입장에서 `ChangeEvent.Version`은 다음을 가능하게 한다:

- "이 이벤트가 현재 내가 캐싱한 버전보다 새것인가?" 판단 (stale event 필터링)
- `GET /mvcc/kv/{key}?version=N` snapshot read와 상관 관계 확인
- CAS 충돌 추적: 소비자가 version을 보고 충돌 여부를 독립적으로 판단 가능

### ChangeLog

```go
// ChangeLog manages CDC subscriptions and event fan-out.
//
// Design constraints:
//   - Slow consumers MUST NOT block apply() (backpressure isolation).
//   - Goroutine leaks MUST NOT occur on Unsubscribe or ctx cancellation.
//   - Publish MUST be non-blocking from the caller's perspective.
type ChangeLog struct {
    mu          sync.RWMutex
    subscribers map[uint64]*subscription // id → subscription
    nextID      atomic.Uint64

    // history retains recent events for offset-based replay.
    // Protected by mu. Capped at historyLimit.
    history     []ChangeEvent
    historyLimit int

    // baseOffset is the Raft log index of the first event in history.
    // Events before this index have been GC'd and cannot be replayed.
    baseOffset  int64
}

type subscription struct {
    id   uint64
    ch   chan ChangeEvent // bounded buffer; see §Slow Consumer Trade-off
    done chan struct{}    // closed by Unsubscribe to signal consumer exit
}
```

#### Subscribe / Unsubscribe

```go
// Subscribe registers a new subscriber and returns a receive-only channel.
// bufSize controls the channel buffer depth (recommended: 256–1024).
// The caller must call Unsubscribe(id) when done to release resources.
func (cl *ChangeLog) Subscribe(bufSize int) (id uint64, ch <-chan ChangeEvent)

// Unsubscribe removes the subscriber and closes its channel.
// Safe to call from any goroutine. Idempotent.
func (cl *ChangeLog) Unsubscribe(id uint64)
```

**goroutine 누수 방지 설계:**

구독자 채널을 `close()`하는 시점이 핵심이다. 다음 두 시나리오를 모두 안전하게 처리한다:

1. **소비자가 먼저 사라지는 경우** (HTTP 클라이언트 연결 끊김):
   - SSE 핸들러의 `ctx.Done()`이 발동 → 핸들러가 `Unsubscribe(id)` 호출
   - `ChangeLog`는 해당 subscription을 삭제하고 채널을 close

2. **서버가 먼저 종료되는 경우** (graceful shutdown):
   - 서버 `ctx.Done()` → `ChangeLog.Close()` 호출
   - 모든 subscriber 채널을 close → SSE 핸들러의 `for event := range ch` 루프 종료

`Publish()`는 채널이 이미 닫혔거나 가득 찬 경우에도 패닉하지 않는다:

```go
func (cl *ChangeLog) Publish(event ChangeEvent) {
    cl.mu.RLock()
    subs := make([]*subscription, 0, len(cl.subscribers))
    for _, s := range cl.subscribers {
        subs = append(subs, s)
    }
    cl.mu.RUnlock()

    for _, s := range subs {
        select {
        case s.ch <- event:
            // delivered
        default:
            // slow consumer: drop (see §Slow Consumer Trade-off)
            // metrics counter: cdc_events_dropped_total{subscriber_id=s.id}
        }
    }
}
```

#### Slow Consumer 처리 — drop vs block vs bounded buffer

이것은 이 ADR에서 가장 중요한 trade-off다.

**Option A: block (unbuffered 또는 full blocking send)**

```go
s.ch <- event  // apply() goroutine이 소비자를 기다림
```

- 장점: 소비자는 이벤트를 절대 놓치지 않음 (at-least-once 완벽 보장)
- 단점: **apply() goroutine이 느린 소비자에 의해 블록됨.** Raft state machine의
  apply 루프는 Raft 클러스터 전체의 처리량에 직결된다. 단일 느린 HTTP 클라이언트가
  Raft commit 전파를 멈출 수 있다. DDIA §"Reliability" 위반.

결론: **불가**. apply() 경로는 외부 소비자에 의해 블록돼서는 안 된다.

**Option B: drop (non-blocking send, 버퍼 초과 시 이벤트 버림)**

```go
select {
case s.ch <- event:
default:  // drop
}
```

- 장점: apply()는 절대 블록되지 않음. 시스템 처리량에 영향 없음.
- 단점: 소비자가 이벤트를 놓칠 수 있음. at-most-once semantics.
- 완화: 소비자는 `?offset=N`으로 replay를 요청해 갭을 메울 수 있음.

**Option C: bounded buffer + drop (이 ADR의 선택)**

```go
// subscriber channel: buffered(256)
// Publish: non-blocking select → default: drop + metrics
```

- 채널 버퍼(256)는 순간적인 burst를 흡수한다. 정상 부하에서는 drop이 발생하지 않음.
- 버퍼가 가득 찬 경우에만 drop. 소비자는 dropped 이벤트를 offset replay로 복구.
- apply()는 절대 블록되지 않음.
- 드롭 시 `cdc_events_dropped_total` 카운터 증가 → 알람 트리거 가능.

**선택 근거:**

이 설계는 **apply() 격리를 최우선**으로 한다. Raft state machine의 apply 루프는
클러스터 내 모든 노드에서 동기화되어야 하며, 외부 소비자의 소비 속도에 종속돼서는
안 된다. 이것은 DDIA Ch.11의 "log-based message broker" 철학과 일치한다:

> "Kafka maintains a separate log for each consumer group, allowing consumers
> to process messages at their own pace without affecting producers."

Core-X의 bounded buffer + drop은 이 철학을 단순화한 형태다.

**이 trade-off가 깨지는 조건:** 모든 소비자가 극단적으로 느리고, 버퍼(256)가 상시
가득 찬 상태라면 모든 이벤트가 drop된다. 이 경우 소비자는 사실상 polling과 다름없다.
**모니터링 신호:** `cdc_events_dropped_total` rate가 높으면 소비자 처리량을 점검하거나
버퍼 크기를 늘려야 한다.

### apply() 후 발행 — at-least-once semantics

#### 발행 시점 선택: commit 후 vs apply 후

**Option A: Raft commit 후 발행 (commitIndex 갱신 시점)**

```
Raft commit (quorum) → commitIndex 갱신 → ChangeEvent 발행
                                    ↓
                             apply()는 아직 실행 안 됨
```

- 장점: 발행 지연 최소화 (apply 전에 알림)
- 단점: apply가 실패할 수 있음 (durable write 실패 등). 발행 후 apply 실패 →
  소비자는 존재하지 않는 상태 변경을 구독. **데이터 불일치.**
- 단점: apply 이전이므로 MVCC version이 아직 결정되지 않음 → `ChangeEvent.Version` 불가.

결론: **불가**. apply 전 발행은 phantom event를 만들 수 있다.

**Option B: apply() 성공 후 발행 (이 ADR의 선택)**

```
apply(entry):
  1. CAS 체크 (충돌 시 → conflictResults, return)
  2. versions[key] 갱신, latest[key] = nextVer
  3. lastApplied.Store(entry.Index)   ← 이 시점 이후
  4. notifyWaiters(entry.Index)
  5. changeLog.Publish(ChangeEvent{...})  ← 발행
```

- 장점: state machine에 실제로 반영된 변경만 발행. phantom event 없음.
- 장점: `ChangeEvent.Version`이 확정됨 (ADR-022 MVCC 연동).
- 단점: apply 후 발행 → process crash between step 3 and step 5 → 소비자가 이벤트를
  놓칠 수 있음. **at-least-once**, 단 at-most-once에 가까운 동작.
- 단점: crash 후 재시작 시 Raft log replay → apply() 재호출 → Publish 재호출 →
  소비자가 같은 이벤트를 두 번 받을 수 있음 (at-least-once).

**정확히는 at-least-once semantics다:**

- Crash 없는 정상 경로: exactly-once에 가까운 at-least-once
- Crash 후 replay 경로: 중복 이벤트 가능 → 소비자가 `Offset`으로 중복 제거

**Exactly-once가 불가능한 이유:**

DDIA Ch.11은 exactly-once를 distributed system에서 달성하는 것이 얼마나 어려운지
설명한다. Core-X에서 exactly-once를 보장하려면:

1. "어떤 offset까지 발행했는지" 상태를 내구적으로 저장 (persistent cursor)
2. Raft log에 "CDC 발행 완료" 항목을 commit (이중 쓰기)
3. 또는 2PC (two-phase commit) — apply와 발행을 원자 트랜잭션으로 묶음

이 모든 방법은 apply() 경로에 내구성 I/O를 추가하며, 처리량과 복잡도 비용이 크다.
learning scope에서는 at-least-once + 소비자 측 멱등성(idempotency)이 실용적이다.

**CAS 충돌 이벤트는 발행하지 않는다:**

```go
// CAS 충돌: state machine 상태 변경 없음 → 이벤트 없음
if cmd.ExpectedVersion > 0 && current != cmd.ExpectedVersion {
    sm.conflictResults[entry.Index] = current
    sm.notifyWaiters(entry.Index, nil)
    return  // ← Publish 호출 없음
}
```

CAS 충돌은 Raft에 commit되지만 state machine 상태는 변경되지 않는다 (INV-MV3).
따라서 CDC 이벤트도 없다. 소비자는 실제 상태 변경만 수신한다.

### MVCCStateMachine 통합

`MVCCStateMachine`에 `*ChangeLog` 필드를 추가한다. `nil`이면 CDC 비활성화 (하위 호환).

```go
type MVCCStateMachine struct {
    // ... 기존 필드 유지 ...
    changeLog *ChangeLog // nil = CDC disabled (backward-compatible)
}

func (sm *MVCCStateMachine) apply(entry LogEntry) {
    // ... 기존 로직 (CAS 체크, version 갱신, gc, lastApplied.Store) ...

    sm.lastApplied.Store(entry.Index)
    sm.mu.Unlock()

    sm.notifyWaiters(entry.Index, nil)

    // CDC 발행: apply 성공 후, WaitForIndex 해제 후
    if sm.changeLog != nil {
        sm.changeLog.Publish(ChangeEvent{
            Type:      cmd.Op,
            Key:       cmd.Key,
            Value:     cmd.Value,
            Version:   nextVer,
            Offset:    entry.Index,
            Timestamp: time.Now(),
        })
    }
}
```

**발행 순서 (notifyWaiters 이후):**

`notifyWaiters`를 먼저 호출하는 이유: HTTP handler의 `WaitForIndex`는 apply 완료를
기다린다. CDC 발행이 느린 소비자에 의해 지연되더라도 (drop이 일어나지 않는 경우)
HTTP handler가 먼저 응답을 보내야 한다. 발행은 부수 효과이지 핵심 경로가 아니다.

### Offset Replay

소비자는 `?offset=N`으로 특정 offset부터 replay를 요청할 수 있다.

```go
// History는 ChangeLog 내에 최근 N개 이벤트를 보관한다.
// historyLimit 초과 시 가장 오래된 이벤트부터 제거.
func (cl *ChangeLog) ReplayFrom(offset int64) ([]ChangeEvent, error)
```

**Replay 한계 — snapshot 이전 offset은 재생 불가:**

Raft snapshot이 설치되면, snapshot index 이전의 Raft log entry는 삭제된다 (ADR-017).
`ChangeLog.history`도 메모리에만 존재하며, 서버 재시작 시 초기화된다.

따라서:

```
Snapshot index: 1000
요청: ?offset=500  → 에러 (baseOffset > 500)
요청: ?offset=1001 → 성공 (history에 존재)
```

이 한계는 의도적이다. Production CDC 시스템(Kafka, Debezium)도 log retention 기간을
초과한 offset replay를 지원하지 않는다. 소비자는 이 경우:

1. 현재 latest offset부터 구독 시작
2. 전체 state snapshot을 `GET /mvcc/kv/{key}` 로 직접 조회
3. 이후 CDC stream으로 incremental 구독

이 패턴은 DDIA Ch.11 §"Replication logs and CDC" 의 "initial snapshot + ongoing stream" 패턴이다.

### SSE vs WebSocket vs Long-polling

#### 선택: SSE (Server-Sent Events)

**SSE:**
```
GET /cdc/stream HTTP/1.1
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

data: {"type":"set","key":"stock","value":"90","version":2,"offset":42,...}

data: {"type":"set","key":"stock","value":"80","version":3,"offset":43,...}
```

- **단방향**: 서버 → 클라이언트. CDC의 의미론과 정확히 일치.
- **HTTP/1.1 표준**: 별도 프로토콜 업그레이드 불필요. Go `net/http`의 `http.Flusher`로 구현.
- **자동 재연결**: 브라우저 `EventSource`는 연결 끊김 시 자동 재연결 + `Last-Event-ID`로 resume.
- **인프라 친화적**: 일반 HTTP reverse proxy(nginx, Envoy)에서 투명하게 동작.

**WebSocket:**
- 양방향 통신이 필요할 때 사용. CDC는 서버 → 클라이언트 단방향이므로 over-engineering.
- HTTP 업그레이드 핸드쉐이크 복잡도 추가.
- 일부 인프라(오래된 프록시, CDN)에서 WS 지원 불안정.

**Long-polling:**
- 클라이언트가 요청을 반복해야 하므로 효율이 낮음.
- 이벤트 간 간격이 짧을 때 (Core-X처럼 고빈도 쓰기 시) 요청 폭발 위험.
- offset 기반 재개 구현이 클라이언트에 복잡도를 전가.

**결론:** SSE는 단방향 이벤트 스트리밍의 표준이다. Go `http.Flusher` 인터페이스로
10-20줄 구현 가능. WebSocket이나 long-polling보다 구현 단순도와 인프라 호환성 모두 우위.

**SSE가 깨지는 조건:** HTTP/2 multiplexing 환경에서 SSE는 자동으로 단일 스트림으로
관리된다. HTTP/1.1에서는 브라우저 per-origin connection limit (6개)이 문제될 수 있으나,
Go 서버 간 통신(서비스 mesh)에서는 무관하다. 현재 Core-X 사용 시나리오에서 문제 없음.

### HTTP API

| Method | Path | Description |
|---|---|---|
| `GET` | `/cdc/stream` | SSE 스트림 구독 (latest offset부터) |
| `GET` | `/cdc/stream?offset=N` | offset N 이후 이벤트 replay 후 live 구독 |
| `GET` | `/cdc/status` | 현재 baseOffset, latestOffset, subscriber count |

#### SSE 핸들러 스케치

```go
func (h *CDCHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    flusher, ok := w.(http.Flusher)
    if !ok {
        http.Error(w, "streaming not supported", http.StatusInternalServerError)
        return
    }

    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")
    w.Header().Set("X-Accel-Buffering", "no") // nginx SSE 버퍼링 비활성화

    // offset replay (snapshot 범위 내)
    if rawOffset := r.URL.Query().Get("offset"); rawOffset != "" {
        offset, _ := strconv.ParseInt(rawOffset, 10, 64)
        events, err := h.changeLog.ReplayFrom(offset)
        if err != nil {
            http.Error(w, "offset out of range: "+err.Error(), http.StatusBadRequest)
            return
        }
        for _, ev := range events {
            writeSSEEvent(w, ev)
        }
        flusher.Flush()
    }

    // live 구독
    id, ch := h.changeLog.Subscribe(256)
    defer h.changeLog.Unsubscribe(id)

    for {
        select {
        case ev, ok := <-ch:
            if !ok {
                return // ChangeLog closed (서버 종료)
            }
            writeSSEEvent(w, ev)
            flusher.Flush()
        case <-r.Context().Done():
            return // 클라이언트 연결 끊김
        }
    }
}

func writeSSEEvent(w http.ResponseWriter, ev ChangeEvent) {
    data, _ := json.Marshal(ev)
    fmt.Fprintf(w, "id: %d\ndata: %s\n\n", ev.Offset, data)
}
```

**goroutine 누수 방지 보장:**

- `defer h.changeLog.Unsubscribe(id)`: 핸들러가 어떤 경로로 종료되든 반드시 실행.
- `r.Context().Done()`: 클라이언트 연결 끊김 시 핸들러 즉시 종료.
- `ChangeLog.Close()`: 서버 shutdown 시 모든 subscriber 채널 close → range 루프 종료.

## Invariants

| ID | Invariant |
|---|---|
| INV-CDC1 | CDC 이벤트는 apply() 성공 후에만 발행된다. CAS 충돌 항목(INV-MV3)은 이벤트를 생성하지 않는다. |
| INV-CDC2 | `ChangeEvent.Offset`은 Raft log index와 동일하다. 단조 증가하며 중복이 없다 (재시작 전까지). |
| INV-CDC3 | `ChangeEvent.Version`은 `MVCCStateMachine.latest[key]`와 동일하다 (INV-MV1에서 파생). |
| INV-CDC4 | `Publish()`는 apply() goroutine을 절대 블록하지 않는다. 느린 소비자는 drop을 받는다. |
| INV-CDC5 | `Unsubscribe()` 또는 서버 종료 후 subscriber goroutine이 남지 않는다. |
| INV-CDC6 | `ReplayFrom(offset)`: offset < baseOffset이면 에러. Raft snapshot GC 이전 이벤트는 재생 불가. |
| INV-CDC7 | at-least-once semantics: 정상 경로에서 각 이벤트는 구독자에게 최대 1회 전달된다. Raft log replay 후 중복 가능. |

## Trade-offs

### 정리표

| 항목 | 선택 | 포기한 것 | 경계 조건 |
|---|---|---|---|
| Slow consumer | bounded buffer(256) + drop | at-least-once 완벽 보장 | drop rate 높으면 소비자 문제 |
| 발행 시점 | apply 성공 후 | exactly-once | crash 후 replay 시 중복 가능 |
| 전달 보장 | at-least-once | exactly-once | 소비자가 Offset으로 중복 제거 |
| 외부 프로토콜 | SSE | WebSocket 양방향성 | HTTP/1.1 per-origin conn limit |
| Replay 범위 | snapshot 이후만 | 전체 이력 재생 | baseOffset < 요청 offset시 에러 |
| CDC 활성화 | opt-in (nil 체크) | 기본 활성화 | 기존 코드 변경 없이 하위 호환 |

### 최적화 대상 명시

이 설계가 최적화하는 것:

1. **apply() 처리량 보장**: CDC 발행이 state machine apply 루프를 절대 블록하지 않음
2. **구현 단순도**: SSE + Go channel fan-out으로 복잡한 message broker 없이 구현
3. **MVCC 통합 자연스러움**: Version 필드가 ADR-022와 동일한 semantics 공유

이 설계가 포기한 것:

1. **Exactly-once delivery**: 분산 시스템에서 exactly-once는 2PC 또는 idempotency key
   필요. Learning scope에서는 at-least-once + 소비자 멱등성으로 충분.
2. **무제한 replay**: Raft snapshot GC 이전 이벤트는 재생 불가. Production에서는
   별도 event store (Kafka, EventStoreDB) 사용.
3. **소비자 offset 관리**: Kafka consumer group처럼 서버가 소비자별 offset을 추적하지
   않음. 소비자 스스로 `Last-Event-ID`를 유지해야 함.

## Consequences

### 긍정적 결과

- 외부 시스템이 polling 없이 변경 사항을 실시간 수신 가능
- MVCC version 포함으로 소비자가 stale 이벤트를 감지 가능
- SSE `Last-Event-ID`로 브라우저 클라이언트의 자동 재연결 및 resume 지원
- apply() 경로 격리: CDC 소비자 문제가 Raft 클러스터에 영향 없음

### 부정적 결과 및 위험

**위험 1: Replay gap 인지 부재**

소비자가 `cdc_events_dropped_total` 메트릭을 모니터링하지 않으면 이벤트 누락을
인지하지 못한다. 누락 감지 자체가 소비자의 책임이다.

완화: SSE `id:` 필드에 Offset을 설정. 브라우저 `EventSource`는 reconnect 시
`Last-Event-ID` 헤더로 마지막 수신 offset을 서버에 전달 → 서버가 replay.

**위험 2: 메모리 growth (history 버퍼)**

`historyLimit` 이내에서 빠른 쓰기가 연속되면 history 버퍼가 최대치까지 차오른다.
기본 `historyLimit=1000`에서 평균 이벤트 크기 1KB라면 ~1MB. 허용 가능.

완화: `historyLimit`을 환경 변수로 조정 가능하게 만든다.

**위험 3: 재시작 후 replay 불가**

서버 재시작 시 `ChangeLog.history`는 비워진다. SSE 클라이언트가 재연결 시
`Last-Event-ID`로 resume을 요청해도, history에 없으면 에러 반환.

완화: 소비자 레벨에서 "gap 감지 후 full re-sync" 로직 구현을 문서화한다.
(실무: Debezium도 connector restart 후 snapshot + replay를 권장한다.)

**위험 4: leader-only CDC 스트림**

`apply()`는 모든 노드에서 실행되지만, CDC 구독은 SSE endpoint를 통해 특정 노드에
연결된다. follower 노드에서도 `apply()`가 실행되므로 CDC 이벤트는 생성된다.
그러나 클라이언트가 follower에 연결하면 Raft commit과 apply 사이에 약간의 지연이
있을 수 있다 (replication lag).

현재 Core-X는 leader redirect를 구현했으므로, `/cdc/stream`도 leader redirect를
따라가도록 클라이언트를 유도한다. 이를 문서화한다.

## Safety

| 항목 | 보장 | 확인 방법 |
|---|---|---|
| apply() 블로킹 없음 | `Publish()`는 non-blocking select | 벤치마크: `go test -bench=BenchmarkApplyWithCDC` |
| goroutine 누수 없음 | `defer Unsubscribe()` + `ChangeLog.Close()` | `goleak` 통합 테스트 |
| race 없음 | `mu sync.RWMutex` 보호, `nextID atomic.Uint64` | `go test -race` |
| 이벤트 순서 보장 | 단일 goroutine (`apply()`에서 발행) → 구독자 채널으로 순서 유지 | 통합 테스트 순서 검증 |
| CAS 충돌 이벤트 없음 | apply() 충돌 경로에 Publish 없음 (INV-CDC1) | 단위 테스트 |

| 위험 | 가능성 | 영향 | 완화 |
|---|---|---|---|
